# Design — Epic: Formatting Fidelity (honor spec §5 via the AST)

**Status:** approved design, pre-implementation-plan. **Date:** 2026-05-16.
**Owner:** core/ast, core/formatter, core/parser. **Captured as:** a GitHub
`epic` issue per `PROCESS.md` (see §6).

## 1. Problem

PR #339 shipped a deliberate stopgap (recorded in ADR-014): the formatter routes
an entry body through the AST **only when**
`render(buildBodyAst(body)) === body` byte-identically; otherwise it keeps the
original string verbatim ("safe conditional fallback").

That stopgap has four consequences:

1. The body-AST is only ~half load-bearing — roughly half of valid Markdown
   rides the string path (a thorough review measured 16/34 probed constructs
   failing the byte-identical guard).
2. Spec §5.2's _enumerated, permitted_ canonical normalizations are not applied
   **through** the AST — the formatter bails to raw instead of normalizing.
3. §5.1 prose-loss bugs in `buildBodyAst` (emphasis dropped, hard line breaks
   fused, thematic breaks deleted) are **masked** by the fallback rather than
   fixed — a §5.1 contract breach hidden, not resolved.
4. The non-round-tripping "surface" is unknown and unmeasured, so "reduce it"
   has no baseline.

## 2. Goal

Make the AST pipeline genuinely satisfy the existing spec §5 round-trip contract
(`docs/specs/markspec-core-data-model.md` §5):

- **§5.1** — the builder is _faithful_: lossless for prose it must preserve.
- **§5.2** — the formatter applies the enumerated permitted rewrites _through
  the AST_ (the "tweaks that can be explained" already listed in §5.2),
  deterministically.
- **§5.3 / §5.4** — idempotent, total, lossless for unowned content.
- The raw-string fallback shrinks toward zero; any residual is explicit and
  diagnosed, not silent.

§5 stays the normative contract — it already defines the right thing. This epic
fixes the _implementation_ to honor it. ADR-014's "non-total inverse / string
fallback" caveat is progressively retired as the surface shrinks.

## 3. Decomposition (sequential: SP1 → SP2 → SP3)

Each sub-project is independently shippable and gets its own spec → plan →
implementation cycle.

- **SP1 — Characterize the lossy surface.** An executable fidelity-matrix
  harness + a generated, committed catalogue. Bounds and classifies the surface;
  makes "reduce" a measurable number. _Zero production-code change._ (Detailed
  in §4 — this is the first sub-project taken to plan.)
- **SP2 — Faithful builder.** Eliminate the `LOSS` class SP1 identifies: make
  `buildBodyAst` capture the §5.1 prose constructs it currently drops
  (emphasis/strong, hard line breaks, thematic breaks, link reference
  definitions, …). Success = SP1 matrix `LOSS` count → 0.
- **SP3 — AST-equivalence formatting contract.** The formatter applies §5.2
  normalizations _via_ the AST; correctness becomes `build(format(x))`
  AST-equivalent to `build(x)`; SP1's provisional `astEquivalent` is
  ratified/hardened as the formal relation; the byte-identical guard is replaced
  and the fallback shrunk to the documented residual; §5 / ADR-014 updated.
  Success = SP1 matrix `NORMALIZE` handled by the formatter, `UNREPRESENTABLE` →
  ∅ (or an explicit, diagnosed, spec-recorded residual).

The epic is "done" when the matrix shows only `OK` / `UNOWNED` (§5.4) entries
plus, at most, an explicitly spec-listed residual.

## 4. SP1 — detailed design (first sub-project)

### 4.1 Deliverables

1. `tests/e2e/ast_fidelity_matrix_test.ts` — a CI-runnable characterization
   harness (Deno test; e2e tier — it exercises `core` build/render/format as a
   black box).
2. `docs/product/ast-fidelity-matrix.md` — a **generated**, committed catalogue
   (deterministic markdown table + per-class summary counts), regenerated by the
   harness.
3. `scripts/check_ast_fidelity_matrix.sh` — a staleness CI gate mirroring
   `scripts/check_tokens.sh`: fails CI if the committed catalogue does not match
   what the harness regenerates.

### 4.2 Corpus

Every body construct the MarkSpec spec permits, derived from
`docs/specs/markspec-core-data-model.md`:

- §2.4 block types: Paragraph, List (ordered/unordered/nested/ loose/tight),
  Table, Figure, Code (tagged/untagged), Feature (gherkin), Math,
  DefinitionList, Note (all admonition kinds), Blockquote.
- §2.5 inline: emphasis, strong, combined emphasis, inline code, inline links,
  reference-style links + their definitions, autolinks, hard line breaks
  (two-space and backslash), entity refs (`$Identifier`), modal keywords (RFC
  2119 / EARS).
- §2.4.1 excluded constructs (heading, thematic break, task list, raw HTML) —
  characterized as a category (expected `UNOWNED`/ diagnostic, must not be
  destroyed).
- Edge cases: nesting, blank-line runs, CRLF, tabs, leading/ trailing
  whitespace, mixed-block bodies.

The corpus is **data-driven** — a table of `{name, markdown}` samples — so it is
extendable in SP2/SP3 as new cases surface. Bounded to the CommonMark + GFM +
GLFM subset the spec allows in an entry body; NOT all of Markdown.

### 4.3 Mechanism (Approach A — provisional AST-equivalence)

For each corpus sample `s`:

1. `ast0 = buildBodyAst(s)`
2. `r = render(ast0)`
3. `ast1 = buildBodyAst(r)`
4. Classify with a provisional pure relation `astEquivalent(a, b)` — structural
   deep-equality of `BodyBlock[]` that **ignores `SourceRange`** (positions
   legitimately move under formatting) and compares node `kind` + textual
   content + markers:

| Class             | Condition                                                                        | Owns                                                  |
| ----------------- | -------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `OK`              | `r === s`                                                                        | — (already round-trips)                               |
| `NORMALIZE`       | `r !== s` ∧ `astEquivalent(ast0, ast1)`                                          | SP3 — §5.2: representation differs, meaning preserved |
| `LOSS`            | `r !== s` ∧ `¬astEquivalent(ast0, ast1)`                                         | SP2 — §5.1: the AST itself changed/lost info          |
| `UNOWNED`         | block is `Unknown` carrying verbatim `raw` (excluded construct / profile-future) | acceptable — §5.4                                     |
| `UNREPRESENTABLE` | spec-permitted prose collapsed into `Unknown`/raw fallback                       | residual — SP3 must close or spec-record              |

5. Secondary cross-check column (Approach C, supplementary — not the
   classifier): does `render(ast0)` agree with the current string-path
   `format()` output for `s`? Recorded for signal, not used to classify (the
   string path is itself incomplete).
6. Idempotence column: `render(buildBodyAst(r)) === r`.

`astEquivalent` lives in the harness/util as a pure function. **SP3 ratifies and
hardens it as the formal §5 contract relation** — SP1 deliberately produces the
asset SP3 needs.

### 4.4 Generated catalogue

The harness emits, deterministically (corpus order):

```text
| Construct | Class | r==s | idempotent | str-fmt agrees | delta (input→render) |
```

plus a summary block: counts per class + a single headline number ("surface =
LOSS + UNREPRESENTABLE = N"). Committed to
`docs/product/ast-fidelity-matrix.md`; the staleness gate keeps it honest.

### 4.5 Behaviour & CI stance

SP1 is **pure measurement — zero production-code change**. It does **not**
modify `build`/`render`/`formatter`. It does **not** fail CI on `LOSS` /
`NORMALIZE` / `UNREPRESENTABLE` entries — those exist today and are the
_baseline_ SP2/SP3 drive down. CI failure conditions for SP1 are only: (a) the
committed catalogue is stale (harness output changed without the doc being
regenerated), or (b) the harness/`astEquivalent` unit tests fail. SP2 and SP3
later add hard assertions ("`LOSS` count must be 0", etc.) as they retire each
class.

### 4.6 Testing

The harness is the primary surface. Additionally, focused unit tests for
`astEquivalent` — its correctness is load-bearing for every classification:

- same structure, different `SourceRange` → **equivalent**
- a dropped emphasis / fused hard break → **not equivalent**
- reordered vs same-order children → not equivalent
- `Unknown(raw=x)` vs `Unknown(raw=y)` → not equivalent; same raw → equivalent

### 4.7 Risks & mitigations

| Risk                                                     | Mitigation                                                                                                           |
| -------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Provisional `astEquivalent` is wrong → misclassification | Dedicated unit tests (§4.6); SP3 hardens it as the formal relation                                                   |
| Corpus incompleteness → undercounts the surface          | Data-driven, extendable; SP2/SP3 add cases as discovered; the headline number is explicitly a lower bound until then |
| Catalogue diff noise                                     | Deterministic corpus ordering + staleness gate                                                                       |
| Scope creep into "fixing" losses                         | SP1 charter is measurement-only; fixes are SP2/SP3                                                                   |

## 5. Out of scope (SP1)

- Any `build`/`render`/`formatter` behaviour change (SP2/SP3).
- Formalizing/normative AST-equivalence in the spec (SP3 ratifies).
- Eliminating any loss (SP2).
- The broader nextgen `MSL-P/I/M/F` migration (ADR-012's separate phase) and
  M050/M051 (ADR-014 deferral) — unrelated.

## 6. Epic capture (PROCESS.md)

Per `PROCESS.md` issue hierarchy: create a GitHub **epic** issue (`epic` +
`epic:formatting-fidelity` + `initiative:markspec` labels) whose body links this
design doc and carries a task list of three child **story** issues — SP1, SP2,
SP3 — each with `Epic: #<N>` as its first body line and an
`epic:formatting-fidelity` label. SP2/SP3 stories stay light until their own
brainstorm; SP1's story points at its forthcoming implementation plan.

## 7. Success criteria

- **SP1:** harness + generated catalogue + staleness gate merged; the catalogue
  reports a concrete classified surface (baseline number); `astEquivalent`
  unit-tested; zero production-code change; `just check` green.
- **Epic:** the matrix ends at only `OK`/`UNOWNED` (+ at most an explicit
  spec-recorded residual); §5 honored via the AST; ADR-014 fallback caveat
  retired.
